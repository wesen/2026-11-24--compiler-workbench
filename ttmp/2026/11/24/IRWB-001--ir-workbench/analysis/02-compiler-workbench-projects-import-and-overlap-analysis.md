# Compiler Workbench projects import and overlap analysis

## TL;DR

`Compiler Workbench_ projects.zip` is **"Compiler Workbench: projects · typed → RV32"**. It is a self-contained browser workbench for one *real* compiler: the **Typed** language from `ds-js-os`/PicoCalc, compiled to **RISC-V RV32IM** machine code and run on an emulator in the page. The book's motto is *"a workbench, not a compiler"*. The compiler exists so you can see what it knows at each step, where every piece came from, and why each change was allowed.

It was built by Claude, apparently as a claude.ai artifact project:

- The build paths are `/home/claude/wb2/`.
- The agent calls `claude.use('sample')`.
- The tests load the reference compiler from `/home/claude/wesen/2026-10-20--ds-js-os/picocalc-os/`.

**Overlap with IR Workbench v6.** The two share no code: plain classic-script JavaScript versus strict TypeScript, and unrelated IR models. They do share a **strong conceptual core**: exact revisions, edits through transactions, provenance, declared effects and preservation, cached facts that go stale, "checked, not assumed" acceptance, linked inspector views, and a workbench that can read its own source. Beyond that core, each has a large part the other lacks:

- **v6 is broad and generic.** It has adapters for many native IRs, Strategy IR, semantic contracts and an incremental task runtime with cache explanations.
- **Compiler Workbench is deep and usable.** It has a complete compiler with dataflow analyses, a real backend and emulator, differential testing against three baselines, projects as plain files with scripts, a reactive UI DSL, a Claude agent with one `eval` tool, and a live book whose every number is measured.

The combination proposal is in [design-doc/01](../design-doc/01-combining-ir-workbench-v6-and-compiler-workbench.md).

## 1. What was imported

The zip (1.4 MB, 26 files) contains only the **built site**. Its authored sources exist only *inside generated bundles*:

- `app/sources.js` (676 KB) embeds every source file, so that `wb.source` can read the running code. It also includes the book Markdown, the API reference and the test scripts, which are not in the zip as files.
- `app/content/projects.js` packs 44 projects; `book.js` and `reference.js` hold the book and the reference.

So the import **unpacks the bundles back into the original repo layout** that `test/build.mjs` expects, and leaves the bundles out (all of them are regenerated by `build.mjs`):

```
sources/compiler-workbench-projects/
  site/            the hand-written site, byte-identical to the zip
    index.html, app/engine/*.js (9), app/ui/*.js|css (9), vendor/{typed-wasm,rv32-interp}.js,
    app/content/references.js   (kept: built from the external reference compiler, not regenerable here)
  src/reference.md              API reference (wb.help, Reference view, agent context)
  src/book/01..17-*.md          the book "Inside the Compiler Workbench"
  src/projects/<id>/...         44 projects + index.json (order)
  test/build.mjs, load.mjs, projects.mjs
```

The import has 237 files and takes 2.0 MB. `scripts/03-verify-compiler-workbench-import.py` reads the zip and confirms the round trip **data-for-data**:

- every non-generated site file is identical
- all 42 embedded sources equal the imported files (only the `<title>` of `index.html` differs between the embedded and shipped copies)
- all 44 projects equal `src/projects/` in order and content
- all 17 chapters and the reference equal `src/`

## 2. What it is

### 2.1 The compiler pipeline

1. The **front end** is reused from the repo: lexer, type checker, and stack code with source spans (`vendor/typed-wasm.js`).
2. The **store** lifts that code into functions, blocks, statements and value trees. This is revision **r0**.
3. **Passes** produce r1…rN, one revision per pass that changes something.
4. **Instruction selection** tiles value trees, a **linear-scan register allocator** assigns registers, and frames are built.
5. The repo's **encoders, disassembler, division magic numbers and RV32 emulator** are reused (`vendor/rv32-interp.js`).
6. An **image** is an entity whose instructions *cover* statements and values.

The repo's own compiler (`typed-rv32.js`) is used only as an **oracle**: reference images built at build time, stored in `app/content/references.js`.

### 2.2 Three rules the API keeps (book, chapter 1)

1. **Readable, immutable entity ids.** Examples: `s:blend.7`, `v:blend.12`, `insn:blend+0x1c@r6`, `fact:liveness(blend)@r2`. Handles are read-only proxies; an assignment or a misspelt member fails with an error code and a "fix:" line.
2. **Change goes through passes.** A pass declares `needs` (facts), `writes` (values, stmts, locals, cfg) and `preserves`. It changes the program only through `tx`, and each change records its **origin** (what it was made from) and its **because** list (what makes it valid). An undeclared write rolls the pass back; facts the pass did not preserve go stale.
3. **Meaning is checked, not assumed.** After every pass the program runs on generated inputs beside r0, and result, trap and memory must agree. Images are checked on the emulator, and the r0 evaluator is checked against the reference compiler's image.

### 2.3 Engine (`site/app/engine/`, ~2,960 lines)

| File | Role |
| --- | --- |
| `store.js` | Entity store, ingest from the front end, lifting to blocks, revisions as snapshots, provenance (`lineage`, `why`) |
| `analyses.js` | Worklist dataflow solver over lattices (set, flat, interval with widening, map); cfg, dominators, loops, liveness, reaching definitions, ranges; fact cache with stale marking |
| `passes.js` | Transactions, pass builder, pass manager, pipelines (O0, O1, O2, loops, checks, broken); built-in passes fold, simplify, constprop, dce, cfg, licm, lvn, strength, bce, subst, and a deliberately wrong `div-to-shift` |
| `evaluator.js` | Interpreter for statements (the definition of meaning), case generation, revision and image checks |
| `backend.js` | Tiling, linear scan, frames, encoding, images, `asmDiff`, `heat` |
| `handles.js` | Guarded proxies, lazy selections (`where/op/line/table…`) |
| `projects.js`, `api.js`, `base.js` | Projects as files, the `wb` root, errors, did-you-mean, YAML |

### 2.4 UI (`site/app/ui/`, ~2,650 lines of JavaScript plus 970 lines of CSS in the "Kiln" design system)

- **Dock.** Drag tabs between tiles, split tiles, choose from layout presets.
- **Linked selection.** Selecting something in Source, IR, CFG or RV32 highlights everything related in the other views.
- **Views.** Lineage, Facts, Pipeline, Timeline, Checks, Run and Console.
- **Projects** are folders of plain files: `project.json`, `*.typed`, `scripts/*.js` (workbench scripts), `ui/*.js` (UI scripts) and `notes.md`. Edits are kept in browser storage as an overlay on the built-in projects.
- **UI DSL** (`dsl.js`). Reactive cells (`ui.query`, `ui.from`, `ui.state`, `ui.param`, `ui.derive`) and components (table, chart, stat, diff, slider…) let a project add its own tiles. A query that has side effects is refused.
- **Fragments** add members to handles without changing the engine. **Parameters** add sliders and toggles to the Pipeline view.
- **Agent** (`agent.js`). One tool, `eval(code)`, whose code runs with `wb, p, project, ui, src, book` in scope and returns YAML. It has three modes (Auto, Ask, Read-only) and takes a snapshot before every step so any step can be reverted. It reads the workbench's own source and book (`src.grep`, `book.search`). It needs the claude.ai artifact sampling capability.

### 2.5 Content

- **44 projects** in 12 groups: Start here, Folding, Control flow, Loops, Bounds, Calls, Broken on purpose, Division, Registers, Writing passes, Programs. Together they have 70 functions in about 480 lines of Typed. Many have scripts and UI tiles; `wrong-shift` is a pass that is wrong on purpose.
- **Book.** 17 chapters in four parts (workbench; passes and facts; meaning and machines; projects and the agent). About 18k words with the reference, linked live to projects, chapters, source lines and entities. The book states that every number in it was measured on the workbench itself. Example: Blend goes from 96 to 88 bytes and from 531 to 451 instructions executed. Across all 44 projects, the r0 evaluator and the reference images agree on all 6,986 decided cases, as do the O2 images.

### 2.6 Maturity and caveats

- **Tests.** There is no unit-test suite. `test/projects.mjs` validates the whole corpus: front end, reference image, O2 pipeline with a check after each pass, image check, and every script on a fresh copy.
- **Hard-coded paths** in the tests and build (`/home/claude/wb2/`, `…/ds-js-os/picocalc-os/compiler/typed-rv32.js`). In the local `~/code/wesen/2026-10-20--ds-js-os`, the reference compiler is now at `compiler/typed/typed-rv32.js`.
- **The vendored front end is out of date.** `vendor/typed-wasm.js` is an older build ("Direct Wasm emitter for PicoCalc world sources") that differs from the current `compiler/typed/typed-wasm.js` in `ds-js-os`.
- **No module system.** Classic scripts populate `globalThis.WB` so the same files load in a `<script>`, in Node `vm` and through `wb.source`. There is no type checking.
- **State lives in the browser.** It stays in memory and browser storage only. The agent needs the claude.ai runtime.
- **Code is more readable than v6's but still dense in places:** 168 UI lines and 90 engine lines are longer than 200 characters.

## 3. Overlap with IR Workbench v6

### 3.1 At a glance

| | IR Workbench v6 | Compiler Workbench |
| --- | --- | --- |
| Thesis | Reusable framework for compilers over *many* meaningful representations | One real compiler as a lab: see what it knows, where things came from, why changes were valid |
| Domains | CAD bracket, game scenes, linkage, door; v6 labs: expressions, scenes, meshes, constraints | Typed → RV32 (integer and memory programs: loops, buffers, records, enums, calls) |
| Language and build | Strict TypeScript, esbuild, ~1 MB of source, 371 `node:test` tests | Plain JavaScript classic scripts, a content generator, ~450 KB, one corpus runner |
| Output | One 11.7 MB offline HTML | Multi-file static site (~1.4 MB) |
| Origin | Multi-agent AI build (role-assigned agents) | Claude artifact project |

### 3.2 Concept by concept

| Concern | IR Workbench v6 | Compiler Workbench | Overlap |
| --- | --- | --- | --- |
| IR model | Native storage behind an `IRAdapter` projecting entities and typed relations (containment, dependency, binding, adjacency, provenance) | One fixed store: functions, blocks, statements, value trees, plus ops, instructions and images | **Conceptual.** CW's store is effectively one adapter |
| Identity | `{artifact, revision(hash), entity}`; content hashes; logical ID vs revision | Readable ids with revision suffixes (`@r6`); linear revisions r0…rN with snapshots | **High** in intent; v6 hashes content, CW is linear and readable |
| Editing | `beginEdit()` → update, insert, remove, connect, redirect → `commit({verify})`; stale and ABA rejection; adapter `rebuild` | `tx.make/const/set/insert/remove/move/rewrite`; required `because` on removals; `undeclaredWrite` rollback | **High** |
| Provenance | Many-to-many correspondence (merge, split, create, delete) composed across revisions and artifacts; `ctx.derive` | Per-entity `origin` plus `because`; `lineage` down to front-end ops; `why` trees; instructions cover statements | **High, and complementary.** CW explains *why it was valid*; v6 handles merge/split across artifacts |
| Pass declarations | Contracts: requires, ensures, establishes, preserves (check or transfer), effects, cache, correspondence | `needs`, `writes`, `preserves` (enforced) | **Medium-high.** CW's declarations are a lightweight contract |
| Facts and analyses | `AnalysisManager`: analyses, properties, facts per exact revision, invalidation epochs, checked transfer | Lattice dataflow solver with widening, six built-in analyses, per-revision fact cache marked stale | **Medium.** Same caching discipline; CW has real dataflow, v6 has semantic properties |
| Meaning and acceptance | Exact domain checkers as acceptance gates (BigInt polynomials, convex fan error, row space) | Differential testing after every pass: r0 evaluator vs head, emulator image, reference compiler image; compares result, trap and memory | **Same principle, different method.** Exact vs sampled; both say "checked, not assumed" |
| Orchestration | Strategy IR: 13 operators as serializable data; fork and chooseBest with metrics and constraints; budgets | Pipelines O0, O1, O2…; builder `pipe`, `repeat('unchanged')`, `checkEach`; `explain()` | **Low-medium.** CW's pipeline is roughly v6's sequence plus repeatUntilStable |
| Incremental runtime | Task, pass and artifact runtime; dependency manifests; cache explanations; warm runs and origin invocations | None beyond the fact cache | v6 only |
| Matching and rewriting | Declarative patterns (`op`, `capture`, `sameAs`, `where`), seven schedules, budgets, cycle detection, match evidence | Imperative `tx.rewrite` bottom-up visitor | v6 only |
| Backend and machine | — | Tiling, linear scan, frames, encoders, disassembler, emulator, `asmDiff`, `heat` | CW only |
| UI | IR lab panels, compiler passes, strategy trace, entity lineage, native YAML editor | Dock with drag layouts, linked selection, Source/IR/CFG/Lineage/Facts/Pipeline/Timeline/Checks/RV32/Run/Console | **Medium.** Similar inspector ideas; CW's shell is more usable |
| Extensibility | Edit native YAML; edit authored TS models (transpiled in a worker); new adapters in code | Projects as files, workbench scripts, UI DSL, fragments, parameters, console | CW much richer |
| Agent | — | Claude agent, one `eval` tool, modes, revert | CW only |
| Self-inspection | Embedded source catalog, Implementation tab | `wb.source` (read, grep, outline, find); book links to `src:` lines | **High** |
| Documentation | 53-page user guide (API, semantics, troubleshooting) | 17-chapter live book plus a reference used by `wb.help` and the agent | Both strong; CW's is interactive |
| Verification | 371 tests and experiment ledgers; browser never run | Corpus runner across 44 projects; numbers in the book are measured; no unit tests | Complementary |

### 3.3 How much overlap?

- **Code: none.** Nothing is shared and nothing can be lifted directly from one into the other.
- **Concepts: about half of each project's ideas.** The shared core is the middle layer: revisioned store, transactional edits, provenance, declared writes and preservation, stale facts, check-before-accept, linked inspection and a self-reading workbench.
- **Unique to v6 (breadth):** representation adapters, Strategy IR, the formal contract vocabulary, declarative patterns and schedules, the incremental task runtime and cache explanations, and multi-artifact correspondence.
- **Unique to CW (depth and usability):** a complete compiler with real dataflow, a backend and emulator, differential testing, the reference-compiler oracle, projects/scripts/UI DSL/fragments/parameters, the agent and the live book.

The two are close to orthogonal around a shared spine, which makes them good to combine. v6 has the better *kernel abstractions*; CW has the better *product* and a real, non-toy domain.
