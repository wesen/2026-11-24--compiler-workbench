# Candela inventory for the Typed chain

## 1. Purpose

Design-doc 03 proposes compiling Candela's scene programs through one artifact chain, Candela → WGSL → Typed → `typed.blocks` → RV32, so that passes on the Typed code can use facts known at the Candela level. This document measures what the existing Typed form of Candela (the ds-js-os gallery program) needs from `typed.blocks`. It records where today's domain (an i32-only port of Compiler Workbench) falls short, and orders the work. All numbers were measured in this repository on 2026-11-24, against ds-js-os b19062b, with the vendored front end.

## 2. The program

The gallery program is `apps/typed/candela-gallery` in ds-js-os. Its `app.json` concatenates five sources in this order:

| file | lines | origin |
|---|---:|---|
| `types.typed` | 166 | hand-written record and enum types |
| `compiler/typed/lib/math.typed` | — | the Typed standard math library |
| `kernel.typed` | 3,146 | Candela's fixed kernel, generated by `tools/gen/candela/kernel-typed.mjs` |
| `scenes.typed` | 3,332 | the gallery's 18 scene sections, generated by the same tool |
| `glue.typed` | 306 | the entry points and the host interface |

Compiled together, the front end produces **332 functions**. The program runs on the ESP32-P4 (RV32IMAFC): the reference compiler `typed-rv32.js` emits RV32F instructions (`fadd.s`, `fmul.s`, `fdiv.s`, `fsqrt.s`, `fcvt.w.s`). The vendored interpreter `bench/host/rv32-interp.js` executes them, with rounding modes, and gives `fcvt.w.s`/`fcvt.wu.s` the saturating semantics of the ISA. The interpreter is therefore an oracle for floating-point behaviour as well as integer behaviour.

## 3. What the front end does with it

Two front-end limits matter:

1. **Source size.** The concatenated source is larger than the front end's default input limit of 64 KiB. `typedWasm.compile` raises `SyntaxError: input limit exceeded` unless it is given `maxSourceLength` (1 << 22 was used here).
2. **The inspection path.** With `inspect: { emit }`, which our lifter uses to obtain each operation with its source span, compilation fails with `Error: unknown tape opcode 151 at 12`. Without inspection, `typedWasm.compileFunctions(source, 0, [], 1 << 22, undefined, onFunction)` delivers every function's tape, and `typedTape.decode(fn.code)` decodes **all 332 tapes without error**. The fault is therefore in the inspection decoder's handling of an operation this program uses and the Compiler Workbench corpus does not. It is an upstream issue to report in ds-js-os, not a property of the program.

The consequence for the lifter: Candela can be lifted from the raw tape. Operations then carry no source span. That loses nothing the chain needs, because provenance for Candela runs through the WGSL generator, whose own source map ties Typed functions to Candela kernel and scene functions; it does not run through Typed source lines.

## 5. What each layer must gain

The work follows the layers of the domain. Each step has an independent check.

1. **Values carry a type.** `typed.blocks` values gain `type: 'i32' | 'f32'`. Locals already record their types. The validator must check operand types per operator. The adapter projects the type as an attribute, so the change set of a pass shows type changes.
2. **Lifting from the raw tape.** A second lifter entry point consumes `compileFunctions` and `typedTape.decode`, with the same stack discipline as `lift` (materialization before stores, calls and control). It accepts the new operations, and its ops have `at: null`. The inspection path stays the default for programs it handles, so the corpus keeps its source lines.
3. **Evaluator semantics.** f32 arithmetic uses `Math.fround` after every operation. `min_num`/`max_num` return the non-NaN operand when exactly one operand is NaN. `to_i32`/`to_u32` follow RISC-V `fcvt.w.s`/`fcvt.wu.s` with round-toward-zero and saturation (NaN gives 2^31−1). Memory holds f32 as IEEE single bits. `text.checked_address` traps outside its bounds. The vendored interpreter decides every disputed case: the reference compiler's image and our evaluator must agree on generated cases, which is exactly the check that already gives 6,986/6,986 on the corpus.
4. **Pass soundness on floats.** `fold` may fold f32 only through `Math.fround`, and must not fold an expression whose result depends on the rounding mode. `simplify`'s identities are i32 identities and must not fire on f32 (`x * 0` is not `0` for NaN or infinity, `x + 0` is not `x` for −0). `strength` and `ranges` stay i32-only, and `lvn`, `licm` and `subst` are type-agnostic. Each pass's rule set is restricted by value type, and a test feeds f32 counterexamples (NaN, ±0, ±∞) through the meaning check.
5. **Backend.** f32 values live in F registers. Instruction selection gains tiles for the RV32F operations above, and linear scan gains a second register class, with calling-convention rules for `fa0`–`fa7`. This is the largest single step, and it builds on the i32 backend (P2.5).
6. **Candela facts.** Two facts are available at the Candela level and invisible in Typed:
   - the scene index `K.scene`, a constant per gallery entry, on which the kernel dispatches;
   - the packed row layout of each scene's data.

   Specialization substitutes the scene constant at the dispatch and lets `cfg` and `dce` remove the other seventeen scenes' code. That is the per-scene specialization experiment of design-doc 03 (P4.3). The fact enters `typed.blocks` as a `because` naming the Candela artifact, so `why` explains a removed scene branch by the Candela fact that justified it.

## 6. Order and checks

| step | done when |
|---|---|
| typed values and validator | the corpus still round-trips and gives 6,986/14; a mistyped table is refused |
| raw-tape lifter | all 332 Candela functions lift; the corpus lifted both ways gives identical tables apart from `at` |
| f32 evaluator | Candela functions agree with the reference compiler's images on the interpreter for generated cases |
| float-safe passes | O2 on Candela keeps meaning on f32 edge cases; i32 corpus results unchanged |
| f32 backend | our Candela image agrees with the evaluator and with the reference image |
| specialization | per-scene images agree with the general kernel on that scene's inputs; size and instruction counts are reported against the reference compiler's |

Steps 1–3 are domain work in `src/typed/`. Step 5 extends the backend. Step 6 is the experiment the whole chain exists for, and it runs only on the host: the board is not flashed as part of this ticket.
