# Source-first architecture: what changed

## Goal

The old examples encoded a building grammar and bracket recipe inside compiler passes. That demonstrated the evaluator but did not adequately demonstrate a reusable language. In this revision, authoring, elaboration, evaluation, and inspection are distinct. The source editor is the primary view, and the compiler source viewer follows actual invocations.

## Reified programs

The object language has three top-level kinds: `part`, `mechanism`, `scene`. Builder methods return a fresh immutable description; `.build()` validates the data. TypeScript control flow runs while constructing that description. There is no attempt to recover its control flow from a JavaScript AST. Source modules are evaluated by the same builder exports used by the strict Node build. `dsl.source` records the resulting immutable program. `dsl.import` projects embedded programs, providing the derivation edge into the next compiler. The browser captures the exact file set used for each run; a comment-only edit need not change a domain artifact revision.

## Independent lowerings

- **CAD:** authored profile → residual DAG → numeric tape → solved profile. Feature list + solved profile → elaborated history → recognized analytic bracket → mesh → metrics. Source feature names survive in the analytic topology's provenance. CAD tessellation settings are projected separately from feature intent.
- **Scene:** each authored definition → geometry specification → mesh. Occurrence layout, material-slot bindings and appearance are separate artifacts. Each mesh can be reduced independently for each requested divisor. Candidate assembly calculates unique and rendered triangle counts; the shared constrained metric selector selects a feasible candidate. Packaging does not generate any building structure.
- **Physics:** authored body/port/joint graph → recognized four-bar → residual DAG → numeric tape → candidate motion samples → constrained selection. The same tape compiler and least-squares machinery are used by the CAD sketch. Solver settings and policy are separate artifacts.
- **Door:** the author imports actual CAD and mechanism programs. The project composition root supplies the scene planner with CAD mesh and motion import adapters. Scene passes accept ordinary artifact task references. Motion attachment composes local transforms with verified body poses; independent geometry, animation and collision artifacts retain names.

## Reuse and inspection

All new passes use the existing compiler runtime; there is no parallel cache implementation for the editor. The runtime records immutable input snapshots, pass parameters and versions, actual required artifact revisions, cache evidence, metrics, diagnostics and derivations. The inspector reads these records, not simulated progress. Source browsing is indexed from the TypeScript syntax tree at build time; the actual pass registration range is highlighted. The browser uses existing view providers for geometry and motion and syntax-highlighted YAML for other IRs. The compiler invocation sidebar and the selected pass inspector share a single lower workspace, with a selectable dependency route above them. This route represents one actual branch of the request graph, not a fabricated linear sequence. YAML is a view/export projection only; JSON remains the runtime data model and trace format.

## How to extend

1. To make a new scene, author a TypeScript program using the same scene API. Names and number of definitions/occurrences are not fixed. The pavilion is a concrete proof; automated tests also add a chimney and compile a differently structured abstract scene.
2. To add a shape vocabulary, extend the shape union/validator and provide a corresponding primitive lowering or import adapter. The runtime, optimizer selector, query database and workbench do not need to change.
3. To add another solver, expose a compatible numerical result artifact and register an algorithm; the existing selection strategy operates on verified metrics. General joint topologies require new recognition/lowering and solver semantics, not simply another string in the API.
4. To add another visual representation, register a view provider by IR kind. No pass needs UI knowledge.

## Verification

The `source-experiments` directory is generated by the actual evaluated source modules and contains complete traces, per-run final artifacts, source snapshots, and execution counts. `test-results.tap` contains the old framework regression suite plus the new source-language tests. `browser-results.json` contains the real browser checks. No outputs are screenshots pretending to be live compilation. See README for exact limits and reproducible commands.
