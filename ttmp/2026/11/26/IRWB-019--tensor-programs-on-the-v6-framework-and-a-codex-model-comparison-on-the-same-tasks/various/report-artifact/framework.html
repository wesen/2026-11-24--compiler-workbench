Part one · the framework

The v6 framework: what it is for, and how a compiler is built on it

The goal of this research is a compiler framework that people can use to build new compilers, IRs, passes and optimizations, and then study them, because every step is checked, recorded and measured. It should be versatile, solid, composable, reusable, extensible and theoretically sound. Two very different languages run on it so that each test of that claim is real: Typed, compiled to RV32, and Tix, compiled to CUDA.

The framework lives in {{src:src/framework|src/framework/}}, about 11,500 lines of TypeScript with no runtime dependencies. It was imported from a prototype (v6) at the start of the project ({{src:ttmp/2026/11/24/IRWB-001--ir-workbench/analysis/01-ir-workbench-v6-import-analysis.md|the import analysis}}) and extended by every stage since. It does not define a universal IR. Each domain keeps its own native data structure and tells the framework three things about it: how to see it as a graph, what it means, and which changes it allows. The framework provides what is common across domains: revisions, edits, correspondence, checking, evidence, caching and orchestration.

The ideas that hold it together

  • A revision is identified by its content. An artifact carries its kind, schema version and two SHA-256 hashes. The contracts manager recomputes them, so a stale fact cannot be attached to changed data: "an artifact cannot pass a contract merely by claiming the expected kind or supplying an old revision next to changed data."
  • Every edit is a transaction. A draft is tied to the exact head and its generation. prepare() rebuilds the native value and reprojects it, rejecting any entity that was silently lost or invented. commit() runs the semantic verifier and publishes only if it accepts. A rejected candidate never advances the head.
  • Correspondence says where each entity went. Each revision step records one-to-one, split, merge, insertion and removal relations between entity IDs. They compose across steps, so traceEntity can follow an instruction back to the source statement that produced it. The README is precise about its limit: "Correspondence records association, not semantic equivalence."
  • Facts have an assurance level. A fact is declared (asserted, never enough to satisfy a requirement), checked (a checker ran), transferred (carried across a correspondence by a registered transfer rule) or proof (an external certificate verifier accepted it).
  • Meaning is checked on each run (translation validation). The framework never assumes a pass is correct. Its contract compares the output with a baseline on generated cases. The evidence records the method (sampled), the seed, the case count, the agreeing, disagreeing and inconclusive cases, and the first counterexamples. A check with no decided case fails, because it has established nothing.
  • Pipelines are data. A strategy plan can be validated, diffed, edited and serialized, and its execution trace names every algorithm version it ran. "Choose the pipeline with the fewest executed instructions" is the operator chooseBest with a metric, not a script.

Part one · worked examples

Four worked examples from the code

Each example below is quoted from the repository at the pinned commit. Together they show how the layers fit together: a same-IR pass, a meaning check, a lowering across IR kinds checked on a GPU, and a domain that uses every layer.

1. A Tix pass, from declaration to verdict

{{src:src/tensor/passes.ts|tensor/passes.ts}} · {{src:src/tensor/index.ts|tensor/index.ts}}

Both Tix passes share one declaration. The pass writes only tensor entities and the reads and contains relations, and returns a new native module. The framework checks the rest.

function pass(name: string, transform: (fn: Fn) => Fn) {
  return definePass<Module>({
    id: 'tensor.' + name, version: '1', description: name,
    ir: TixIR, adapter,
    writes: { entities: ['tensor'], relations: ['reads', 'contains'] },
    run: ({ before }) => ({ native: { functions: before.value.functions.map(transform) } }),
  });
}
export const inlinePass = pass('inline', inline), splitPass = pass('split-sum', split);

optimizeTix applies each pass with a meaning gate, and the relation is chosen per pass. inline must be exact, because substituting a pointwise expression does not change any rounding. split-sum turns sum(k) into a sum over blocks of a sum over lanes. That changes the order of addition, so it is checked under a tolerance. A rejection comes back as data, with the first counterexample:

const result = applyNativePassSync(definition, current,
  meaningGate(origin, pass === 'inline' ? 'exact' : 'tolerance'));
// on rejection:
{ pass, accepted: false, changed: false, reason: 'at [3,1] expected 1065353216, got 1065353218, allowed 0' }

The values in the rejection are illustrative; the format is that of the compare function in the next example. Under the exact relation it compares f32 words, so values appear as integers.

2. The meaning gate: a differential check as an invariant

{{src:src/tensor/contract.ts|tensor/contract.ts}} · {{src:src/framework/contracts/differential.ts|contracts/differential.ts}}

The gate builds cases from the origin program and evaluates each side with the f32 interpreter. differential() wraps that as an invariant the framework understands. Under the exact relation the baseline is the revision before; under tolerance it is the origin, so tolerances cannot accumulate across passes.

const baseline = relation === 'exact' ? before : origin;
const invariant = differential<typeof ports, Sample, BufferValue>({
  id: 'tensor.meaning.' + relation, version: '1', inputs: ports,
  baseline: 'baseline', subject: 'subject', seed, count: samples.length,
  cases: () => samples,
  run: (side, artifact, s) => side === 'baseline'
    ? s.reference
    : evaluate(artifact.value.functions.find(f => f.name === s.fn)!, s.inputs, 'f32'),
  compare: (a, b) => compare(a, b, relation),
});
const evidence = runDifferential(differentialSpec(invariant), { baseline, subject: candidate });

The cases are where most of the strength lies, and agents found that weak cases let bad passes through. A research agent showed that a pass confusing two equal-sized dimensions was accepted when every shape symbol got the same size. Since F21 every symbol gets a distinct size, and empty extents are checked too.

3. Lowering to CUDA: a transformation across IR kinds, decided on a GPU

{{src:src/tensor/cuda-contract.ts|tensor/cuda-contract.ts}}

The lowering takes a tensor.tix artifact to a tensor.cuda-source artifact. Its check is the same differential(), but nothing runs locally: decide receives every undecided case at once and runs them in one remote batch. If the source has a launch-time gate, every case is run on both sides of it.

cases: ({ baseline, fn, subject }, random) => {
  const samples = cudaCases(selectFunction(baseline.value, fn), random);
  return takesGate(subject.value.source)
    ? samples.flatMap(s => sides.map(gate => ({ ...s, gate })))
    : samples;
},
// The case list depends on the subject only through whether it has a gate.
baselineKey: ({ baseline, fn, subject }) =>
  JSON.stringify([baseline.revision, fn, takesGate(subject.value.source)]),
subjectKey: (_a, _c, { subject }) => JSON.stringify([subject.revision, profile]),
async decide({ baseline, fn, subject }, cases, todo) { /* one GPU batch per gate side */ }

The keys make verdicts reusable. A second check of the same source and compiler profile costs nothing, and concurrent cold checks share one in-flight batch (F19). The comment above baselineKey is a claim, and since F26 the framework checks it. On a reuse hit it regenerates the cases, compares a canonical digest, and throws a ContractError if the cases depend on more than the key.

4. Typed: every layer at once

{{src:src/typed/passes.ts|typed/passes.ts}} · {{src:src/typed/strategies.ts|typed/strategies.ts}} · {{src:src/typed/rules/verify.ts|typed/rules/verify.ts}}

The Typed domain is where the framework is used most fully. Its passes declare dataflow analyses as needs, so the manager computes them once per revision. Correspondence comes from the origin records each edit wrote and from the because of each removal, so the workbench's why can walk any instruction back to the front end. The contract checks that the program still means what r0, the unoptimized original, meant, by running both in an RV32 emulator on generated cases.

const pass = definePass<TypedBlocks, Record<string, any>, Record<string, unknown>>({
  id: `typed.${spec.name}`, version: '1', description: spec.about,
  ir: BlocksIR, adapter: blocksAdapter,
  needs,                                                   // dataflow analyses, cached per revision
  writes: { entities: [...writes.entities], relations: [...writes.relations] },
  preserves: (spec.preserves ?? []).map(n => ANALYSES[n]), // claims the framework checks
  run({ before, facts, params }) { /* the pass body, through a Tx on a working copy */ },
});

Pipelines are strategy plans. fastest runs four pipelines and keeps the one whose image executes the fewest instructions on the project's own cases:

fastest: { choose: { O0: 'O0', O1: 'O1', O2: 'O2', loops: 'loops' }, by: 'instructions' },
cleanup: { repeat: ['cfg', 'fold', 'simplify', 'constprop', 'dce'] },   // until nothing changes

Rewrite rules are data, and each is verified once for all inputs of its types, by the strongest methods that apply. The verifier records which method established it, so a rule's assurance is explicit:

Part one · honest limits

Where the framework's promises have not held up

Most of what the framework promises held under two domains. The places where it did not are listed here, because they set the next stages' work.

Checks are sampled, not proven

Every meaning check that guards a pass is a differential test on generated cases. Its evidence is labelled checked-sampled. The proof assurance exists only as a slot for an external certificate verifier, and the README says so: "This framework does not contain a theorem prover." The case generator carries the strength, and it has been wrong twice: equal shape sizes before F21, and a tolerance whose absolute term accepts an all-zero output below 2e-6 (F22, open). Exact relations and verified rules are the way out, and that is where programme A (A0, running now) starts.

Lowering decisions bypass the pass machinery

Fusion groups, thread or block mode, staged terms and the launch gate are decided by planFusion and the emitter, in plain TypeScript. The CUDA artifact is a source string whose only entities are kernel names (F24). The framework checks the meaning of the result, but none of the individual decisions, and none of them is composable as a pass. Stage 6 exists to fix this: a schedule IR whose every scheduling step is a checked pass.

Correspondence and keys were trusted

Correspondence promised traceability, but its entity lists were whatever the caller declared, until F23. Verdict reuse promised safety, but it trusted the spec's key, until F26. Both were found by agents comparing their own results, not by design review. Tix passes still declare coarse writes (all tensor entities) and return a whole new module, so their correspondence is no finer than "the module changed".

The rewrite engine and the strategy IR are barely used by Tix

The IR layer has a pattern matcher with seven rewrite schedules, scoped edit authority and failure statuses. No Tix pass uses it, because whole-function rewrites were simpler. The strategy IR runs every Typed pipeline but no Tix one. A framework whose second domain skips two of its layers has not yet shown those layers are general.

Two runners with different powers

applyPass is asynchronous and supports analysis needs, preservation claims and manager-dependent contracts. applyNativePassSync, added for Tix, refuses all three. Simple passes are easier this way, but a domain has to choose between simplicity and the framework's checking of preservation.

Measured choice is not a cost model

chooseBest picks the pipeline that measures best per project, and that works. A fixed preset does not. speed takes the bytecode VM from 7,678 to 9,286 executed instructions, the only one of six corpus programs it makes worse. Nothing in the framework predicts cost from the IR; D1, running now, is finding out why from the correspondence records.

Trust boundaries, from the READMEs: adapter callbacks, predicates, rewrite bodies and verifiers are trusted TypeScript; read-only facades constrain capabilities but are not a sandbox; cache: 'pure' is not a security boundary; the revision store is in memory.
