Part three · method

How we compare the agents' work

Most of the compiler on this page was written by coding agents. Each stage goes to a matrix of agent configurations, each working from the same brief and the same base revision in its own git worktree, and is then measured. That serves two purposes: the best implementation is merged, and the comparison shows which configurations, briefs and policies produce good compiler work.

The method is written up as a reusable playbook, {{vault:Research/playbooks/agents/PLAYBOOK - Comparing Coding-Agent Configurations on the Same Design-and-Implement Tasks.md|Comparing Coding-Agent Configurations}}, with a companion on {{vault:Research/playbooks/agents/PLAYBOOK - Measuring and Reducing Over-Engineering in Agent-Written Designs.md|measuring over-engineering}}. The launch and judging scripts are in {{vault:Research/playbooks/agents/scripts|the playbook's scripts}}, and the per-experiment ones in the {{src:ttmp/2026/11/26/IRWB-019--tensor-programs-on-the-v6-framework-and-a-codex-model-comparison-on-the-same-tasks/scripts|IRWB-019 scripts}}.

The axes we measure

No single score is trusted. Each axis has its own instrument, and the instruments that a judge cannot bias come first.

AxisInstrumentBias-resistant?
CorrectnessHidden suite against the brief's fixed API; bits against the f32 meaning on corpus, optimized and random programs; every checkLowering verdictyes
PerformanceBenchmark medians at the brief's sizes, alternating variants; held-out programs; geomean and worst case; "never slower than unfused"yes, given the timing protocol

Honest self-reportThe agent gets its own failing inputs and must diagnose each with file:line, without changing codeyes
CostWall time, commands, output tokens, from the session recordsyes
ProcessDiary, committed scripts, tests, and isolation (no reading other agents' branches), checked in the transcriptsyes

Blinding and judging

  • Letters, not names. Ticket IDs carry a letter (IRWB-033-A to J). A seeded shuffle assigns letters to cells, and the key stays in the coordinator's ticket, which no base revision contains.
  • Blind packs. Designs are copied without frontmatter, as doc-A, doc-B and so on. A word-boundary scan checks for model and ticket names, and file counts are compared with the source so that nothing is silently dropped.
  • Two judges from different families. In R2 the Claude judge scored Claude designs 1.5 points higher (of 10), and the Codex judge scored Codex designs 1.75 higher. Each repeated itself within a point, so this is a bias, not noise. Every cross-family ranking averages one judge from each family. With neither judge's family among the authors, the two rankings agreed at Spearman 0.88–0.89.
  • Judges are audited. A script scans each judge's tool calls for paths outside the pack: the key, other worktrees, the coordinator's ticket. None were found in seven Codex judge sessions.

Hidden evaluators and the timing protocol

An implementation stage is scored by a program written from the brief before any agent starts ({{src:ttmp/2026/11/26/IRWB-019--tensor-programs-on-the-v6-framework-and-a-codex-model-comparison-on-the-same-tasks/various/hidden-t3b/t3b-eval.mjs|t3b-eval.mjs}}, {{src:ttmp/2026/11/26/IRWB-019--tensor-programs-on-the-v6-framework-and-a-codex-model-comparison-on-the-same-tasks/various/hidden-t6/t6-eval.mjs|t6-eval.mjs}}). It runs each worktree in its own process, one at a time, after every agent has finished, with the current main as a baseline in the same run. Today's measurement (T9) fixed the timing protocol: 12 interleaved calls on each of 14 program and variant series showed a coefficient of variation of 0.2–1.7% (3.4% for attention) at a steady 2411 MHz SM clock. The median of 5 calls fell within 5% of the median of 12 in every subset, so differences under 5% count as noise.

Briefs and policies

  • Fix only the comparison surface, such as the language core, a three-function API and the pass names, at the generality the corpus uses. When a brief allowed affine parameter types that no program used, twelve of sixteen designs planned a general shape solver.
  • A policy outranks the brief. A policy example that narrowed the brief's grammar was followed by every agent over the brief. Policies are written in the task's own terms, without examples.
  • Policies by stage type. v1 is the baseline. v3 adds rules against over-engineering, which reduced Sol's excess by one or two items at a cost of about half a fitness point. v3r, used for stage 6 and the Typed stages, keeps v3 but asks each agent to try at least one of the brief's invited approaches and report the result, because "prefer the smallest deliverable" would cap a creative stage.
  • Ask for the strongest claim the evidence supports. In stage 2, one implementation was bit-exact by construction and still checked and reported itself under a tolerance.

What the comparisons have shown so far

FindingEvidence
Implementation stages separate configurations far less than research roundsAll cells correct in stages 1, 3 and 3b; new families near Opus on speed. In the research rounds, both judges placed every DeepSeek and GLM design below every OpenAI and Anthropic one.
Hidden programs must differ in structure from visible onesDivision inside reductions reversed stage 3's speed-ups; held-out log-softmax exposed a 6.6× regression.
Agents implement less than they design, and that is usually rightAll 16 stage-1 designs proposed a lazy-edit framework change; 4 of 14 implementations made it.
Self-reports were faithfulAll fourteen stage-1 cells reported their hidden-suite results accurately when shown them.
Codex cells are fastest in wall time4–16 minutes against 43–118 for Claude and Pi cells on the same stage.
Contradictory findings point at real gapsTwo cells reported opposite results on correspondence checking; the code showed both were right, and F23 followed.
