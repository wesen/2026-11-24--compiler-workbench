IR Workbench · tensor track · IRWB-019

A checked tensor compiler on the v6 framework

The IR Workbench's framework was built for one language, Typed, a small scalar language compiled to 32-bit RISC-V. The tensor track tests whether it carries a second, very different domain. Tix is an index-notation language for tensor programs, compiled to CUDA and run on an NVIDIA GB10 over ssh.

Every stage was designed and implemented by several coding agents from one brief, scored by hidden tests, and the best implementation merged. This page has three parts. Part one explains the framework: its layers, four worked examples from the code, what the work added to it, and where it fell short. Part two follows the compiler stage by stage. Part three describes how the agents' work is compared and judged, and what that has shown. Source links point to commit e72865e on github.com/wesen/2026-11-24--compiler-workbench.

The pipeline

A Tix program becomes a v6 artifact, an immutable revision with a content hash. Passes rewrite it, and a meaning gate checks each one against the revision before it. The lowering plans fusion from the IR and prints one CUDA translation unit, a second v6 artifact. The GPU check runs that unit on generated cases and compares every output word with the f32 meaning.

Part one · the framework

The v6 framework: what it is for, and how a compiler is built on it

The goal of this research is a compiler framework that people can use to build new compilers, IRs, passes and optimizations, and then study them, because every step is checked, recorded and measured. It should be versatile, solid, composable, reusable, extensible and theoretically sound. Two very different languages run on it so that each test of that claim is real: Typed, compiled to RV32, and Tix, compiled to CUDA.

The framework lives in src/framework/, about 11,500 lines of TypeScript with no runtime dependencies. It was imported from a prototype (v6) at the start of the project (the import analysis) and extended by every stage since. It does not define a universal IR. Each domain keeps its own native data structure and tells the framework three things about it: how to see it as a graph, what it means, and which changes it allows. The framework provides what is common across domains: revisions, edits, correspondence, checking, evidence, caching and orchestration.

The ideas that hold it together

  • A revision is identified by its content. An artifact carries its kind, schema version and two SHA-256 hashes. The contracts manager recomputes them, so a stale fact cannot be attached to changed data: "an artifact cannot pass a contract merely by claiming the expected kind or supplying an old revision next to changed data."
  • Every edit is a transaction. A draft is tied to the exact head and its generation. prepare() rebuilds the native value and reprojects it, rejecting any entity that was silently lost or invented. commit() runs the semantic verifier and publishes only if it accepts. A rejected candidate never advances the head.
  • Correspondence says where each entity went. Each revision step records one-to-one, split, merge, insertion and removal relations between entity IDs. They compose across steps, so traceEntity can follow an instruction back to the source statement that produced it. The README is precise about its limit: "Correspondence records association, not semantic equivalence."
  • Facts have an assurance level. A fact is declared (asserted, never enough to satisfy a requirement), checked (a checker ran), transferred (carried across a correspondence by a registered transfer rule) or proof (an external certificate verifier accepted it).
  • Meaning is checked on each run (translation validation). The framework never assumes a pass is correct. Its contract compares the output with a baseline on generated cases. The evidence records the method (sampled), the seed, the case count, the agreeing, disagreeing and inconclusive cases, and the first counterexamples. A check with no decided case fails, because it has established nothing.
  • Pipelines are data. A strategy plan can be validated, diffed, edited and serialized, and its execution trace names every algorithm version it ran. "Choose the pipeline with the fewest executed instructions" is the operator chooseBest with a metric, not a script.

Part one · worked examples

Four worked examples from the code

Each example below is quoted from the repository at the pinned commit. Together they show how the layers fit together: a same-IR pass, a meaning check, a lowering across IR kinds checked on a GPU, and a domain that uses every layer.

1. A Tix pass, from declaration to verdict

tensor/passes.ts · tensor/index.ts

Both Tix passes share one declaration. The pass writes only tensor entities and the reads and contains relations, and returns a new native module. The framework checks the rest.

function pass(name: string, transform: (fn: Fn) => Fn) {
  return definePass<Module>({
    id: 'tensor.' + name, version: '1', description: name,
    ir: TixIR, adapter,
    writes: { entities: ['tensor'], relations: ['reads', 'contains'] },
    run: ({ before }) => ({ native: { functions: before.value.functions.map(transform) } }),
  });
}
export const inlinePass = pass('inline', inline), splitPass = pass('split-sum', split);

optimizeTix applies each pass with a meaning gate, and the relation is chosen per pass. inline must be exact, because substituting a pointwise expression does not change any rounding. split-sum turns sum(k) into a sum over blocks of a sum over lanes. That changes the order of addition, so it is checked under a tolerance. A rejection comes back as data, with the first counterexample:

const result = applyNativePassSync(definition, current,
  meaningGate(origin, pass === 'inline' ? 'exact' : 'tolerance'));
// on rejection:
{ pass, accepted: false, changed: false, reason: 'at [3,1] expected 1065353216, got 1065353218, allowed 0' }

The values in the rejection are illustrative; the format is that of the compare function in the next example. Under the exact relation it compares f32 words, so values appear as integers.

2. The meaning gate: a differential check as an invariant

tensor/contract.ts · contracts/differential.ts

The gate builds cases from the origin program and evaluates each side with the f32 interpreter. differential() wraps that as an invariant the framework understands. Under the exact relation the baseline is the revision before; under tolerance it is the origin, so tolerances cannot accumulate across passes.

const baseline = relation === 'exact' ? before : origin;
const invariant = differential<typeof ports, Sample, BufferValue>({
  id: 'tensor.meaning.' + relation, version: '1', inputs: ports,
  baseline: 'baseline', subject: 'subject', seed, count: samples.length,
  cases: () => samples,
  run: (side, artifact, s) => side === 'baseline'
    ? s.reference
    : evaluate(artifact.value.functions.find(f => f.name === s.fn)!, s.inputs, 'f32'),
  compare: (a, b) => compare(a, b, relation),
});
const evidence = runDifferential(differentialSpec(invariant), { baseline, subject: candidate });

The cases are where most of the strength lies, and agents found that weak cases let bad passes through. A research agent showed that a pass confusing two equal-sized dimensions was accepted when every shape symbol got the same size. Since F21 every symbol gets a distinct size, and empty extents are checked too.

3. Lowering to CUDA: a transformation across IR kinds, decided on a GPU

tensor/cuda-contract.ts

The lowering takes a tensor.tix artifact to a tensor.cuda-source artifact. Its check is the same differential(), but nothing runs locally: decide receives every undecided case at once and runs them in one remote batch. If the source has a launch-time gate, every case is run on both sides of it.

cases: ({ baseline, fn, subject }, random) => {
  const samples = cudaCases(selectFunction(baseline.value, fn), random);
  return takesGate(subject.value.source)
    ? samples.flatMap(s => sides.map(gate => ({ ...s, gate })))
    : samples;
},
// The case list depends on the subject only through whether it has a gate.
baselineKey: ({ baseline, fn, subject }) =>
  JSON.stringify([baseline.revision, fn, takesGate(subject.value.source)]),
subjectKey: (_a, _c, { subject }) => JSON.stringify([subject.revision, profile]),
async decide({ baseline, fn, subject }, cases, todo) { /* one GPU batch per gate side */ }

The keys make verdicts reusable. A second check of the same source and compiler profile costs nothing, and concurrent cold checks share one in-flight batch (F19). The comment above baselineKey is a claim, and since F26 the framework checks it. On a reuse hit it regenerates the cases, compares a canonical digest, and throws a ContractError if the cases depend on more than the key.

4. Typed: every layer at once

typed/passes.ts · typed/strategies.ts · typed/rules/verify.ts

The Typed domain is where the framework is used most fully. Its passes declare dataflow analyses as needs, so the manager computes them once per revision. Correspondence comes from the origin records each edit wrote and from the because of each removal, so the workbench's why can walk any instruction back to the front end. The contract checks that the program still means what r0, the unoptimized original, meant, by running both in an RV32 emulator on generated cases.

const pass = definePass<TypedBlocks, Record<string, any>, Record<string, unknown>>({
  id: `typed.${spec.name}`, version: '1', description: spec.about,
  ir: BlocksIR, adapter: blocksAdapter,
  needs,                                                   // dataflow analyses, cached per revision
  writes: { entities: [...writes.entities], relations: [...writes.relations] },
  preserves: (spec.preserves ?? []).map(n => ANALYSES[n]), // claims the framework checks
  run({ before, facts, params }) { /* the pass body, through a Tx on a working copy */ },
});

Pipelines are strategy plans. fastest runs four pipelines and keeps the one whose image executes the fewest instructions on the project's own cases:

fastest: { choose: { O0: 'O0', O1: 'O1', O2: 'O2', loops: 'loops' }, by: 'instructions' },
cleanup: { repeat: ['cfg', 'fold', 'simplify', 'constprop', 'dce'] },   // until nothing changes

Rewrite rules are data, and each is verified once for all inputs of its types, by the strongest methods that apply. The verifier records which method established it, so a rule's assurance is explicit:

Part one · honest limits

Where the framework's promises have not held up

Most of what the framework promises held under two domains. The places where it did not are listed here, because they set the next stages' work.

Checks are sampled, not proven

Every meaning check that guards a pass is a differential test on generated cases. Its evidence is labelled checked-sampled. The proof assurance exists only as a slot for an external certificate verifier, and the README says so: "This framework does not contain a theorem prover." The case generator carries the strength, and it has been wrong twice: equal shape sizes before F21, and a tolerance whose absolute term accepts an all-zero output below 2e-6 (F22, open). Exact relations and verified rules are the way out, and that is where programme A (A0, running now) starts.

Lowering decisions bypass the pass machinery

Fusion groups, thread or block mode, staged terms and the launch gate are decided by planFusion and the emitter, in plain TypeScript. The CUDA artifact is a source string whose only entities are kernel names (F24). The framework checks the meaning of the result, but none of the individual decisions, and none of them is composable as a pass. Stage 6 exists to fix this: a schedule IR whose every scheduling step is a checked pass.

Correspondence and keys were trusted

Correspondence promised traceability, but its entity lists were whatever the caller declared, until F23. Verdict reuse promised safety, but it trusted the spec's key, until F26. Both were found by agents comparing their own results, not by design review. Tix passes still declare coarse writes (all tensor entities) and return a whole new module, so their correspondence is no finer than "the module changed".

The rewrite engine and the strategy IR are barely used by Tix

The IR layer has a pattern matcher with seven rewrite schedules, scoped edit authority and failure statuses. No Tix pass uses it, because whole-function rewrites were simpler. The strategy IR runs every Typed pipeline but no Tix one. A framework whose second domain skips two of its layers has not yet shown those layers are general.

Two runners with different powers

applyPass is asynchronous and supports analysis needs, preservation claims and manager-dependent contracts. applyNativePassSync, added for Tix, refuses all three. Simple passes are easier this way, but a domain has to choose between simplicity and the framework's checking of preservation.

Measured choice is not a cost model

chooseBest picks the pipeline that measures best per project, and that works. A fixed preset does not. speed takes the bytecode VM from 7,678 to 9,286 executed instructions, the only one of six corpus programs it makes worse. Nothing in the framework predicts cost from the IR; D1, running now, is finding out why from the correspondence records.

Trust boundaries, from the READMEs: adapter callbacks, predicates, rewrite bodies and verifiers are trusted TypeScript; read-only facades constrain capabilities but are not a sandbox; cache: 'pure' is not a security boundary; the revision store is in memory.

Part two · the compiler, stage by stage

Stage 1: the Tix language, IR, evaluators and checked passes

merged · IRWB-020-B · Astra

Tix has five constructs: shaped parameters, pointwise expressions, sum and max reductions over named indices, single-assignment statements, and affine index arithmetic. Shapes are inferred and named (N, D), and indices may be affine (x[i + dy, j + dx]). Its f32 meaning is fixed down to the order of accumulation: every literal and operation is rounded to f32, and a reduction starts at 0 or −∞ and adds in increasing lexicographic order of its indices. Implementations can therefore be compared bit for bit.

fn layernorm(x: f32[N,D], gamma: f32[D], beta: f32[D], eps: f32[1]): f32[N,D] {
  mean[i] = (sum(j) x[i,j]) / D;
  centered[i,j] = x[i,j] - mean[i];
  variance[i] = (sum(j) centered[i,j] * centered[i,j]) / D;
  y[i,j] = centered[i,j] / sqrt(variance[i] + eps[0]) * gamma[j] + beta[j];
  return y;
}
What was built
  • A parser with shape inference and affine dimensions.
  • The Tix IR as a v6 artifact (tensor.tix), exposing functions and tensors as entities, definition order as containment and reads as dependencies.
  • f32 and f64 evaluators; the f32 one is the meaning.
  • A meaning gate: sampled shapes and inputs, compared against the revision before. Since F21 every shape symbol gets a distinct size, and empty extents are checked.
  • Two passes: inline, which substitutes a statement into its readers, and split-sum, which splits a reduction (that changes rounding, so it is checked under a tolerance).
  • Framework change: a synchronous native pass path in define-pass.ts, so same-IR passes need no async manager.

Stage 2: lowering to CUDA, checked on the GPU

merged · IRWB-022-I · Astra

Each statement becomes one kernel, and each output element one thread. Every f32 operation is emitted with an explicitly rounded intrinsic (__fadd_rn, __fmul_rn, __fdiv_rn, __fsqrt_rn), so nvcc can neither contract to FMA nor reorder. Transcendentals are computed in double and rounded once, which matches the interpreter's Math.fround(Math.exp(x)) exactly. The result is bit-identical to the f32 meaning by construction, a property three of twelve implementations had and none claimed in its design.

What was built
  • cudaSource: one standalone translation unit with host code that reads cases, launches the kernels, and writes results and CUDA-event times.
  • tools/cuda-remote.mjs: copies a directory to the GB10 keyed by content (identical inputs compile once, about 0.5 s), runs it, and brings out/ back. --timed takes an exclusive GPU lock, so agents sharing the machine do not disturb each other's timings.
  • checkLowering: the lowering as a heterogeneous v6 transformation. Its differential check runs every undecided case in one GPU batch.
  • runTixCuda, with benchmark (a warm-up and the median of three timed launches).
  • Framework changes: none. Heterogeneous transformations and batched decide were enough.

The exact relation, and why it matters

Stage 2's lowering was exact, but it was checked against an f64 reference under a tolerance, |c − r| ≤ 2e-6 + 2e-5·|r|. That tolerance is too weak to catch some bugs and too strong for others. A research agent showed that its absolute term accepts an all-zero output when results are below 2e-6 (F22, open). Since F17, checkLowering compares f32 words exactly against the current revision's f32 meaning. NaN is compared as a class, because the GPU and Node produce different NaN bit patterns.

Exactness is what makes every later stage checkable without arguing about error bounds. A fusion, a tile or a thread mapping that keeps each output's order of operations has to produce the same bits, and any other result is a bug.

Stage 3: checked fusion

merged · IRWB-029-D · Opus

Stage 2 writes every intermediate tensor to global memory, and its row reductions run one thread per row with uncoalesced reads. Stage 3 fuses statements into fewer kernels without changing a bit. planFusion decides groups from the Tix IR: a statement joins a kernel when every read of a kernel member uses that member's own index on the shared leading axes, with matching extents. Two mappings cover the cases:

  • Thread mode keeps stage 2's one thread per element and holds intermediates in registers: elementwise chains and epilogues (mlp's bias and GELU).
  • Block mode gives one block a row, staged in shared memory, or in global scratch when it does not fit. Thread 0 computes each per-row reduction in the meaning's order, with barriers between statements: softmax, layernorm, attention.

Max folds use PTX max.NaN.f32, probed equal to stage 2's max on all 324 special-value pairs. fuse: false still prints stage 2's source byte for byte, pinned by digest in the tests. Every corpus program lowers to one kernel.

Result

Softmax 2.06×, mlp 1.21× faster. On the hidden programs, which divide inside their reductions (sum(d) x[i,d] / D), fused layernorm and attention lost to unfused: the division ran in thread 0's serial loop. A probe showed the same code gains 2.5× on layernorm when the division is outside. That finding defined stage 3b.

Stage 3b: fusion that is never slower

merged · IRWB-030-E · Fable
  • Parallel terms, serial fold. In a costly reduction body (a division, a transcendental, max/min, a nested reduction, or at least four cheap operations, a threshold measured), every thread computes terms into a term area, and thread 0 adds them in order with the same rounded fold. Each term is rounded as before and the sum keeps its order, so the bits are unchanged.
  • Rows written in place when nothing reads the old row later (e over score, centered over x). This fits more blocks per SM, and it is what lifted attention and mlp.
  • A launch-time gate. A block-mode group runs fused when its longest row has at least 96 elements or there are at most 1,024 rows, and its heavy members fill enough lanes. Otherwise the same template kernel runs as per-statement instantiations. checkLowering checks both sides of every gate, and since F25 runTixCuda reports which side ran.

How each stage was checked

Agents' own measurements are reported, but the merge decision rests on a hidden evaluator, written from the brief before any agent's work existed and run one implementation at a time so that GPU timings do not interfere. It checks:

  • corpus programs fused and unfused, optimized programs, and random programs, all bit for bit against the f32 meaning;
  • every checkLowering verdict accepted as exact;
  • kernel counts;
  • benchmark medians at the brief's sizes, plus full-size bits.

Two lessons shaped it. In stage 3, the hidden programs differed in structure from the visible ones (where the division sits), which showed that the agents' performance claims were tuned to the visible corpus. For stage 3b, held-out programs were added that the brief did not name, and they caught the log-softmax regression.

Research rounds

Two design-only rounds asked open questions, scored blind by judges from two model families.

  • R1: derive streaming (Flash-style) attention by checked rewrites. Every OpenAI configuration derived the online-softmax rescaling correctly, as a sequence of rules with side conditions and a new fold construct with a tuple state. It is queued as T5.
  • R2: what would make Tix best in class? All four original cells defined it around the exact meaning: the fastest code that stays bit-identical. Their convergent measurements include an exact tiled 512³ matmul at 0.054–0.058 ms (3.7× faster than stage 2, about 1.7× slower than cuBLAS), and the meaning's arithmetic ceiling (FMUL+FADD 14.4 TFLOP/s against FFMA 27.0). Two cells independently found a parallel fold that is bit-identical to the sequential one. The R2 judge also found the closest prior art, arXiv 2609.11356, which reconstructs cuBLAS's reduction order and checks bitwise equivalence of compiled kernels.

Part three · method

How we compare the agents' work

Most of the compiler on this page was written by coding agents. Each stage goes to a matrix of agent configurations, each working from the same brief and the same base revision in its own git worktree, and is then measured. That serves two purposes: the best implementation is merged, and the comparison shows which configurations, briefs and policies produce good compiler work.

The method is written up as a reusable playbook, Comparing Coding-Agent Configurations, with a companion on measuring over-engineering. The launch and judging scripts are in the playbook's scripts, and the per-experiment ones in the IRWB-019 scripts.

Blinding and judging

  • Letters, not names. Ticket IDs carry a letter (IRWB-033-A to J). A seeded shuffle assigns letters to cells, and the key stays in the coordinator's ticket, which no base revision contains.
  • Blind packs. Designs are copied without frontmatter, as doc-A, doc-B and so on. A word-boundary scan checks for model and ticket names, and file counts are compared with the source so that nothing is silently dropped.
  • Two judges from different families. In R2 the Claude judge scored Claude designs 1.5 points higher (of 10), and the Codex judge scored Codex designs 1.75 higher. Each repeated itself within a point, so this is a bias, not noise. Every cross-family ranking averages one judge from each family. With neither judge's family among the authors, the two rankings agreed at Spearman 0.88–0.89.
  • Judges are audited. A script scans each judge's tool calls for paths outside the pack: the key, other worktrees, the coordinator's ticket. None were found in seven Codex judge sessions.

Hidden evaluators and the timing protocol

An implementation stage is scored by a program written from the brief before any agent starts (t3b-eval.mjs, t6-eval.mjs). It runs each worktree in its own process, one at a time, after every agent has finished, with the current main as a baseline in the same run. Today's measurement (T9) fixed the timing protocol: 12 interleaved calls on each of 14 program and variant series showed a coefficient of variation of 0.2–1.7% (3.4% for attention) at a steady 2411 MHz SM clock. The median of 5 calls fell within 5% of the median of 12 in every subset, so differences under 5% count as noise.

Briefs and policies

  • Fix only the comparison surface, such as the language core, a three-function API and the pass names, at the generality the corpus uses. When a brief allowed affine parameter types that no program used, twelve of sixteen designs planned a general shape solver.
  • A policy outranks the brief. A policy example that narrowed the brief's grammar was followed by every agent over the brief. Policies are written in the task's own terms, without examples.
  • Policies by stage type. v1 is the baseline. v3 adds rules against over-engineering, which reduced Sol's excess by one or two items at a cost of about half a fitness point. v3r, used for stage 6 and the Typed stages, keeps v3 but asks each agent to try at least one of the brief's invited approaches and report the result, because "prefer the smallest deliverable" would cap a creative stage.
  • Ask for the strongest claim the evidence supports. In stage 2, one implementation was bit-exact by construction and still checked and reported itself under a tolerance.

Running now, and next

Stage 6: a schedule IR with checked scheduling passes

running · IRWB-033 · ten cells

The pipeline becomes Tix → schedule IR → CUDA. Tile, split, reorder, bind, stage, vectorize and double-buffer become passes on the schedule IR, each with legality decided from the IR and each checked. The emitter only prints, and a strategy picks the schedule. The target is exact tiled contractions against cuBLAS at 512³ and 4096³, without losing anything fusion gained. The brief invites new approaches: order preservation proven from the IR, correspondence that follows each output's accumulation, an IR-level cost model. The hidden evaluator adds five shapes the brief does not name.

Typed side, in parallel

running · seven cells each
  • D1: why the speed pipeline makes the bytecode VM slower, found by crediting executed instructions to compiler decisions through correspondence, then fixed.
  • A0: what share of O2 and speed edits are local value rewrites, the founding hypothesis for proving functions equivalent from per-rule proofs.
  • B1: specializing the VM on its bytecode, a first Futamura projection over constant memory.
  • Queued: D2, missed optimizations from provenance, which reuses D1's attribution.

Later in the queue: tolerance calibration with mutants (T4), split-K and parallel reductions as IR rewrites (T10), checked FMA contraction (T11), autotuning (T7), the streaming-attention derivation (T5), tensor cores as a checked precision change (T12), and R2's ideas: verified fast intrinsics, a bit-identical parallel fold, and acceptance by proof.
