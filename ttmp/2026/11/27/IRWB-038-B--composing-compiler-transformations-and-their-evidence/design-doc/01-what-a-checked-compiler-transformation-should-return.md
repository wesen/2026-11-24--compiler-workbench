# What a checked compiler transformation should return

## Decision

Make a **validated transformation between named artifact ports** the unit that a strategy can select, cache or publish. Let a domain produce a candidate in its natural representation. Give the candidate a revision-scoped explanation of its edits and give the validator an explicit statement of what must hold. This is a change to who owns acceptance. It does not require rewriting either compiler into a common instruction set.

The motivating experiment takes one real Tix reduction split. Its exact gate rejected it. The stock strategy bridge ran the very same pass, returned a changed artifact and recorded no contract. Supplying a managed correspondence requirement revealed a second problem. The generic edit named the function and parameter as well as its statements, and the contract rejected that universe. Fixing only the async call site would leave both the semantic obligation and the vocabulary of the mapping unresolved. See `src/tensor/index.ts:39`, `src/framework/passes/bridge.ts:39`, `src/framework/passes/define-pass.ts:348`, `scripts/01-pass-boundary.mjs:17` and `scripts/01-pass-boundary.mjs:45`.

## What the comparison changes

### A pass is currently too small to carry its own experiment

The pass spec couples its input IR, adapter, write vocabulary, needs and optional contract to one type S. A native result returns another S. The managed transformation contract already speaks named input and output ports. The CUDA lowering registers baseline, function and fusion option as inputs and CUDA as an output. It hand-assembles the kernel correspondence and calls the planner and emitter inside its body. The direct source and execution APIs separately assemble the lowering. These are three different responsibilities: constructing a candidate, choosing how to lower, and deciding whether the candidate may enter a checked experiment. `src/framework/passes/define-pass.ts:70`, `src/framework/passes/define-pass.ts:79`, `src/framework/contracts/types.ts:137`, `src/tensor/cuda-contract.ts:83`, `src/tensor/cuda-contract.ts:203`, `src/tensor/cuda-contract.ts:221`, `src/tensor/index.ts:66`.

The synchronous native runner prohibits needs, preservation and managed contracts. It requires a host gate on changed candidates. The managed runner resolves needs, supports native results with a lazy edit and can confirm a preservation claim by recomputation. Its gate is optional. The meaningful asymmetry is the *ownership and availability of evidence*. Native computation itself works inside a strategy. The probe deliberately requests exactness for split, which the public Tix optimizer ordinarily checks under tolerance. It compares the same requested relation on the two outputs; it does not diagnose an error in the public optimizer's choice of relation. `src/framework/passes/define-pass.ts:231`, `src/framework/passes/define-pass.ts:250`, `src/framework/passes/define-pass.ts:276`, `src/framework/passes/define-pass.ts:302`, `src/framework/passes/define-pass.ts:373`, `src/tensor/index.ts:42`, `scripts/01-pass-boundary.mjs:15`.

The T6 alternatives form an experiment in API placement. E implements five strategy cases in executeSync; H implements a separate sequence/apply evaluator. J registers fused, tiled and pipelined steps with an explicit gate in the bridge. D adds a synchronous legality predicate consulted by both runners before the body. The D predicate receives before/view/params, so an implementation needing a fact has no declared fact port there. Preserve the distinction between an inapplicable candidate and an incorrect candidate. Carry those outcomes through the existing strategy operators. A ticket prototype registered both native passes with one explicit origin-relative tolerance, ran fork/chooseBest on the existing interpreter, and selected the one-statement result; both arms recorded sampled acceptance (`scripts/07-checked-choice.mjs:18`, `scripts/07-checked-choice.mjs:37`). The J registration is the smallest migration experiment; the D precondition motivates a richer operation signature. **T6-E** `src/framework/strategy/sync.ts:37`; **T6-H** `src/framework/strategy/sync.ts:94`; **T6-J** `src/tensor/schedule-plan.ts:33`; **T6-D** `src/framework/passes/define-pass.ts:101`, `src/framework/passes/define-pass.ts:264`, `src/framework/passes/define-pass.ts:305`; merged `src/framework/strategy/interpreter.ts:487`, `src/framework/passes/bridge.ts:57`.

### The entity universe is part of the type of a correspondence

Tix projects function, parameter and statement entities. Each statement's entire expression is an attribute. Its read relation uses a set of names, so two reads at different index expressions become one dependency edge. Its contract enumerates only statement IDs. The native inline pass returns a module without explicit mappings. On a permuted producer/consumer pair the generic diff retained f/y and removed f/p. It knew which tensor disappeared, but supplied no edge from the inlined producer to the surviving consumer. The lowering is finer: its mapping groups the contributing statement IDs for each kernel. `src/tensor/ir.ts:100`, `src/tensor/ir.ts:105`, `src/tensor/ir.ts:125`, `src/tensor/passes.ts:89`, `src/framework/ir/correspondence.ts:116`, `src/tensor/cuda-contract.ts:95`, `scripts/01-pass-boundary.mjs:27`.

F23 and F24 solve real identity problems. The manager checks the enumerated ID sets against the supplied lists, then checks membership of entries. The generic IR validator additionally requires every endpoint to occur in an entry. A managed transformation requiring a correspondence accepted **zero groups** with both correct lists in the probe. Conversely it rejected a complete generic edit using the adapter's broader universe. A full “statement to selected function's kernels” contract also needs an explicit policy for other functions' statements. Requiring blanket totality across the entire module would make valid function selection look like deletion. `BACKLOG.md:483`, `src/framework/contracts/analysis-manager.ts:1110`, `src/framework/ir/correspondence.ts:85`, `src/framework/ir/correspondence.ts:158`, `src/tensor/cuda-contract.ts:93`, `scripts/01-pass-boundary.mjs:45`.

D1-G joins machine counts to the first covered statement, assigns residual costs to frame/backend and joins new sites through the first origin. D1-D constructs lineage across steps. The census asks “what edit occurred?” and attribution asks “where was work observed?” A change ledger can supply shared input to both, while keeping their measures distinct. `src/typed/rules/compile.ts:124`, `src/typed/tx.ts:47`, `src/typed/passes.ts:128`, `src/typed/attribute.ts:89`, `src/typed/attribute.ts:105`; **A0-G** `src/typed/edit-classes.ts:283`, **A0-C** `tools/edit-census.mjs:21`, **D1-D** `src/typed/attribution.ts:88`. ### A schedule needs an independent statement of legality

The merged planner fuses adjacent producers and consumers by common axis prefix and access form, then decides thread/block mapping, row-buffer reuse, and whether staging is worthwhile. Its cost thresholds and string-valued launch predicate sit beside correctness decisions. Even the runtime recovers the gated kernel names by matching generated CUDA text. A schedule IR should own that information through emission and execution. Retaining a source string as a terminal artifact is fine; recovering the experiment's arm labels from the pretty-printer is avoidable. `src/tensor/fusion.ts:83`, `src/tensor/fusion.ts:107`, `src/tensor/fusion.ts:135`, `src/tensor/fusion.ts:142`, `src/tensor/fusion.ts:229`, `src/tensor/cuda-source.ts:148`, `src/tensor/cuda-runtime.ts:142`, `src/tensor/cuda-contract.ts:187`.

T6-B seeds a schedule from planFusion; G consults it in a scheduling pass; A calls it on fragments; E recomputes it after isolation; C even compares the candidate with another invocation of the planner. C's own interim report describes a foundation with decisions still in the emitter. H converts a fusion plan, I seeds passes from one and J also invokes it on the schedule's program. D goes further by giving split, reorder, bind and stage separate operations, and E evaluates the candidate schedule on samples. Reusing a planner as a *candidate producer* is sensible. Using agreement with it as the only specification would reject a better, legal schedule and accept a shared planner error. **T6-B** `src/tensor/schedule.ts:504`, **T6-G** `src/tensor/schedule-passes.ts:103`, **T6-A** `src/tensor/schedule.ts:268`, **T6-E** `src/tensor/schedule-passes.ts:49`, `src/tensor/schedule-eval.ts:399`, **T6-C** `src/tensor/schedule.ts:61`, **T6-H** `src/tensor/schedule.ts:254`, **T6-D** `src/tensor/schedule.ts:539`, `src/tensor/schedule.ts:633`, `various/01-cell-survey.md:17` through `various/01-cell-survey.md:26`.

There is a concrete distinction between a pass's precondition and an independent output validator. T6-D's order checker tests reduction extents 11, 1 and 0. Interchanging the outer and inner loops of a strip-mined reduction of width 16 agrees on all three. At extent 17 the helper accepted a variant that visits 0,16,1,… instead of 0,1,…,16. With terms 2²⁴, −2²⁴ and 1 at positions 0,1,16, respectively, the two f32 sums were 0 and 1. The public reorder precondition correctly refused the permutation. This isolates the validator's strength and gives a regression fixture for future producers of schedules. No inference about generated GPU code is required. **T6-D** `src/tensor/schedule.ts:298`, `src/tensor/schedule.ts:310`, `src/tensor/schedule.ts:589`; `scripts/05-reduction-order.mjs:12`, `scripts/05-reduction-order.mjs:26`.

### A comparison relation has no intrinsic assurance level

The Tix exact pass compares the immediate predecessor, while tolerance compares against the origin. The CUDA checker takes the current Tix meaning as its reference and compares f32 bits, with NaNs in one equivalence class. It can force both runtime gate arms. These are different judgments even when the report for every one says “agree”. In differential tally, one agreement plus inconclusives can yield agreement. Tix adds an independent nonempty-coverage requirement per function. The differential helper labels any evidence other than method=sampled as checked-exact, including missing or misspelled evidence in the probe. This is a defect in that helper's contract. The property manager separately requires a property-specific verifier to record proof. `src/tensor/contract.ts:125`, `src/tensor/contract.ts:130`, `src/tensor/cuda-contract.ts:100`, `src/tensor/cuda-contract.ts:146`, `src/framework/contracts/differential.ts:283`, `src/framework/contracts/differential.ts:378`, `src/framework/contracts/analysis-manager.ts:885`, `tests/framework/contracts.test.mjs:121`, `scripts/01-pass-boundary.mjs:30`.

The coordinator's “sampled, never proven” is a good description of the merged *meaning gates* discussed here. As a claim about every check it is too broad. Typed distinguishes symbolic-linear, by-construction, reduced-width and sampled rule evidence. A proof about an algebraic schema, a successful match of that schema and a proof covering an entire applied pass are three distinct propositions. A0's denominator disagreement and the schedule-order probe show why the framework should keep them distinct. `src/typed/rules/verify.ts:9`, `src/typed/rules/verify.ts:63`, `src/typed/rules/evidence.ts:16`, `src/typed/passes.ts:224`, `BACKLOG.md:491`, `scripts/05-reduction-order.mjs:15`.

### Who owns publication matters even in a single process

Using the same native inline, I supplied an IRStore to the managed runner. With the default output ID, preparation failed because the store already knew a head for the input ID. With a fresh output ID, the mapping contract rejected the candidate, but the supplied store returned the candidate as the new ID's head. Opening the output view calls retain before contract verification; retain seeds a fresh lineage. This is a result about the caller-supplied IRStore, distinct from the compiler cache and the manager's accepted transformation records. A “prepare” operation must be able to inspect a candidate without creating a published head. `src/framework/passes/define-pass.ts:201`, `src/framework/passes/define-pass.ts:304`, `src/framework/passes/define-pass.ts:350`, `src/framework/ir/view.ts:190`, `src/framework/ir/store.ts:52`, `scripts/01-pass-boundary.mjs:58`.

## Proposed concepts and their smallest instances

The evidence supports extracting the following *interfaces*. The signatures, division of ownership and proposed evaluation criteria are design hypotheses. “Domain” below means the implementer supplies the operators' semantics, layout, aliasing, floating-point model and measurement method. A generic validator cannot infer those by inspecting JSON.

### 1. Partial transformation with a single publication boundary

**Theory.** Model an operation as a partial, typed transformation. A precondition determines applicability. A Hoare-style postcondition relates named inputs and outputs. Sequential composition wires compatible output ports into the next transformation. The MLIR Transform dialect provides a precedent for making a transformation executable over a separate payload with defined failure propagation. [MLIR Transform dialect](https://mlir.llvm.org/docs/Dialects/Transform/)

Proposed interface, in evaluation order:

```text
prepare(spec, inputs, params, factResolver) -> Inapplicable(reason) | Candidate(outputs, edits)
validate(candidate, requiredJudgments, executionCapabilities) -> Validation
publish(candidate, validation, expectedHeads) -> Accepted(outputRefs) | Stale
```

A shape mismatch before constructing a candidate, a counterexample afterward, an unavailable GPU, and a racing head change must have distinct outcomes. Stage all output IDs privately. Publish all or none after validation against the captured revisions. Build on the manager’s existing pre-commit stale-evidence check and verify/commit protocol (`src/framework/contracts/analysis-manager.ts:1524`, `src/framework/contracts/analysis-manager.ts:1588`). On retry, reuse immutable candidate bytes if their dependencies still match and validate against the current policy. A cache hit can therefore still fail publication. A caller studying unchecked outputs may inspect the candidate through an explicit path.

**Instances.** Tix inline supplies one native module and its substitution evidence. Typed LICM requests loop facts and supplies an edit. Tix-to-CUDA supplies a different output type and a device-dependent judgment. Origin/current are explicit ports whenever observable meaning refers to both. Only the host's executor knows whether achieving the requested assurance will suspend. A synchronous public API may use the same phases for operations whose facts and checks can all complete immediately. A general plan may await any of the phases. `src/tensor/passes.ts:82`, `src/typed/passes.ts:429`, `src/tensor/cuda-contract.ts:203`, `src/tensor/contract.ts:125`, `scripts/01-pass-boundary.mjs:58`.

### 2. Revision-scoped provenance relations and rewrite witnesses

**Theory.** Relational composition tracks where entities go across edits and lowerings. A term-rewriting witness records a rule instance, its substitution and discharged side conditions. A structural relation can associate several sources with one target without claiming semantic equality or apportioning cost. Debug instruction references offer a compiler precedent for retaining a logical identity independently of its final machine location. [LLVM instruction references](https://llvm.org/docs/InstrRefDebugInfo.html) and [Lopes et al., verified peephole optimizations](https://web.ist.utl.pt/nuno.lopes/pubs/alive-pldi15.pdf)

```text
Universe = (revision, projectionId, projectionVersion, selection)
Edit = (operation, reads, writes, from: Universe, to: Universe, groups, premises)
Witness = ruleFingerprint × substitution × focusPath × factRefs
checkMapping(edit, coverage: partial | sourceTotal | targetTotal | bothTotal)
attribute(observedWeights, correspondence, allocationPolicy) -> bins + unattributed
```

Enumerate actual members through the named projection. Validate every mapped endpoint, then coverage for that purpose. Creation and deletion use empty endpoints, unknown lineage is an explicit result. Compose only at the same intermediate universe or with a declared projection map. In a term rewrite, replay the witness at its focus, check capture/alias/trap conditions, and compare the whole reconstructed result with the candidate. A matched rule alone covers no sibling edits. Count observations by a declared policy such as exclusive site or shared group. Retain an “indirect” bin. For additive weights, the sum including residuals must equal the original total. End-to-end GPU latency with overlapping kernels has no corresponding default additive allocation.

**Instances.** Inline emits f/p → f/y with its affine substitution; lowering maps statements to kernels, including grouped fusion. Simplify emits the exact rule it just matched. A0 queries local shape, dependence on facts and structural footprint separately. D1 joins observations to the same revision-qualified sites. A common ledger removes the need to reconstruct what the producer already knew and still supports a fallback analysis of historical data. `src/tensor/cuda-contract.ts:83`, `src/typed/rules/compile.ts:125`, `src/typed/attribute.ts:138`, **A0-G** `src/typed/edit-classes.ts:307`, `scripts/01-pass-boundary.mjs:27`.

### 3. Translation-validation judgments with explicit scope and method

**Theory.** Translation validation checks a particular source/target pair under a semantics, potentially using a simulation relation. Differential testing provides observations for selected inputs. The quantifier on the conclusion is part of the result. A universal claim requires a sound verifier and explicit assumptions. [Necula, Translation Validation for an Optimizing Compiler](https://people.eecs.berkeley.edu/~necula/Papers/tv_pldi00.pdf)

```text
Judgment = (referenceRef, subjectRef, semanticsVersions, inputDomain, observation, relation)
Validation = (judgment, method, quantifiedScope, checkerVersion, outcome, evidenceRef)
method ∈ {differential, finiteExhaustion, checkedDerivation, externalCertificate}
outcome ∈ {supported, refuted(counterexample), inconclusive(reason), unavailable(reason)}
```

For sampling, include recipe, seed, comparable/attempted counts, exclusions, per-function and per-arm coverage, profile and counterexamples. For finite exhaustion, require a domain enumeration and cardinality argument. For a checked derivation, bind each premise to its revision and verifier. Unknown evidence cannot acquire a stronger tag. Composition needs a rule for the requested relation: transitive exact equivalence over the same observation and hypotheses can compose; approximate bounds generally accumulate. Two origin-relative tolerances do not establish pairwise equivalence. A mixed pass can carry a proof for a subset of edits and a sample over the whole transformation. Give any universal conclusion only to the subset its proof covers.

### 4. Demand-driven analysis queries with explicit dependency projections

**Theory.** In demand-driven incremental computation, reuse is justified by the inputs a computation actually depends on. In abstract interpretation, a monotone transfer on an ordered abstract domain yields a conservative approximation at a fixed point. The query mechanism owns identity and dependencies; an individual analysis chooses an appropriate algorithm, including a fixed-point solver. [Hammer et al., Adapton](https://www.cs.umd.edu/~mwh/papers/hammer13adapton.html) and [Cousot, Abstract Interpretation](https://www.di.ens.fr/~cousot/AI/)

```text
query(def@version, subjectRef, selection, params) -> (value, dependencies, assurance)
depend(selection, projection@version) -> contentKey
transferFact(old, edit, readFootprint) -> verifiedReuse | recompute
```

Cache a *fact about a region*, including facts consulted across its boundary. Missing facts and negative lookups can affect a result. A changed callee, bound buffer, gate arm or launch profile must invalidate any dependent outcome. A key produced by the domain is a dependency claim. Require sampled recomputation audits during migration and retain conservative whole-artifact invalidation when the dependency projection cannot be justified. Distinguish a cost prediction, a measured cost and a legal transformation in the fact schema.

### 5. Polyvariant specialization with memoized residual control points

**Theory.** Partial evaluation specializes a program for static inputs and residualizes operations on dynamic inputs. In polyvariant specialization the same source location may have several residual versions. Interning a location and static environment before exploring successors allows backedges to close. Termination requires a finite division, generalization or a growth budget. Specializing an interpreter to its program is the first Futamura projection. [Jones, Gomard and Sestoft, Partial Evaluation and Automatic Program Generation](https://raspi.itu.dk/people/sestoft/pebook/toc.html)

```text
specialize(entry, initialStaticEnv, step, liveStaticProjection, generalize, budget)
step(point, env) -> residualOps × [(successor, successorEnv)]
intern(point, canonical(liveStaticProjection(env))) -> residualHandle
```

Two independent responsibilities remain with the domain. The operation semantics determine which reads can be folded under aliasing, trapping and effects. A builder emits blocks, edges, and a designated residual entry. Keep the assumption artifact and any runtime guard or fallback in the result. If generalization loses a static operand, resume residual execution under the weaker environment or report inapplicable before publication. A budget exhaustion cannot turn a partially emitted graph into an accepted program.

### 6. Affine schedule relations with validity dependences

**Theory.** Separate an algorithm from its schedule. Represent dynamic statement instances as integer sets, memory accesses and dependences as relations, and a schedule as a map to an execution order. Every required dependence must have positive lexicographic distance, or a separate synchronization argument for a parallel mapping. The affine model covers a deliberate subset. [Ragan-Kelley et al., Decoupling Algorithms from Schedules](https://people.csail.mit.edu/jrk/halide12/) and [isl manual, schedule constraints](https://libisl.sourceforge.io/user.html)

```text
problem = (parameterDomain, iterationDomains, accesses, requiredOrder, effects)
candidate = (scheduleMap, storageMap, boundsGuards, parallelBindings, synchronization)
validate(problem, candidate) -> valid(certificate) | invalid(instancePair) | unknown
rank(validCandidates, targetProfile, observationProtocol) -> selection
```

Check coverage of the original iteration domain, uniqueness of writes, access bounds, aliasing and validity dependences. For strict f32, model each output's recurrence edge from reduction position k to k+1 and the accumulator initialization. An injective, order-preserving map on reduction steps allows parallel evaluation of *terms* with a serial fold; a reassociated reduction needs a different judgment. Parallel thread order cannot be inferred from the lexicographic order of thread IDs. Make storage scopes, barriers and carried state explicit. An unknown relation yields conservative fallback. Keep hardware occupancy, shared-memory limits and calibration profiles outside the mathematical legality kernel.

For the restricted strip-mine case there is a cheap independent proof obligation. For positive integer T and 0 ≤ k < R, the quotient q = floor(k/T) and remainder r = k mod T are unique. Scheduling by (q,r) with the tail guard qT+r < R is a bijection onto the original iterations and preserves increasing k. Scheduling by (r,q) breaks the required recurrence when R > T. This proof covers arbitrary nonnegative R and positive T under mathematical integer indexing. An emitter additionally owes absence of machine-index overflow and correct accumulator ownership, a different obligation from the bijection. The three-term probe supplies a numerical witness when order is wrong. `scripts/05-reduction-order.mjs:12`.

**Instances.** The existing row fusion needs a same-tile producer availability check. T6 contraction tiling needs ordered reduction, tail coverage and synchronization. Both can consume one access/dependence representation while selecting different schedules. Typed natural loops are a later test only for a recognized affine subset with proven alias bounds. A schedule manifest should drive emitter, runner and gate-arm coverage from the same selected variant. An independent executable oracle or symbolic validator must still test the resulting program. `src/tensor/fusion.ts:97`, `src/tensor/fusion.ts:229`, **T6-D** `src/tensor/schedule.ts:298`, `src/tensor/schedule.ts:633`, `src/tensor/cuda-runtime.ts:142`, `src/typed/analyses.ts:215`, `scripts/05-reduction-order.mjs:15`.

## Alternatives and rejection criteria

**Adopt a universal editable graph.** I would decline. A logical read projection is already sufficient for matching, diff and provenance. **Give each latency mode its own strategy language.** I would decline. The E and H subsets have different operators and traces. **Use pass legality as the semantic checker.** I would decline. **Replace every lowering check with local proofs.** I would decline. An integer rewrite can have a checkable algebraic derivation.
