# Composable transformations and independent evidence

## Decision

Make a **typed transformation between immutable revision tuples** the unit of execution, publication, and inspection. An endomorphic pass, a lowering, and a specialization under static assumptions should produce the same kind of receipt. Keep native representations, exact revision identity, adapter projections, and strategy plans as data. Put eligibility, candidate construction, validation, and commit on one execution path. Make semantic obligations, entity lineage, and performance observations independently queryable.

The evidence for changing the root is that the same Tix kernel can run through the native API, the async API, and a strategy callback with different protection, and the same candidate has different visibility when a store is supplied. Tix CUDA already uses a multi-port transformation while the rich pass layer hard-codes one IR kind. Typed wraps native transactions and reconstructs correspondence in its pass declaration. P6 reproduces a split acceptance state. The manager records acceptance and makes a candidate fact visible before the outer pass rejects on preservation. The existing deferred contract API is the starting point for a fix. See `src/framework/passes/define-pass.ts:79`, `src/framework/passes/define-pass.ts:201`, `src/framework/passes/define-pass.ts:225`, `src/framework/passes/define-pass.ts:347`, `src/tensor/cuda-contract.ts:203`, and `src/typed/passes.ts:168`. P1 exercises the runner and store claims. P6 exercises acceptance order.

The term **evidenced** below means the stated need has direct source, comparative, or probe support. A proposed interface and its estimated payoff are hypotheses. **Conjecture** identifies a larger extension or a second application that still needs a prototype. The [cell inventory](../analysis/01-cell-evidence.md) gives frozen HEADs, line anchors, and the boundaries of the comparison.

## Proposed concepts

### 1. Typed transformations with preconditions and receipts

**Evidenced.** Use partial, typed transformations on tuples of revisions. In Hoare logic, a precondition identifies the states for which an operation is specified and a postcondition states its guarantee. In translation validation, a checker relates the concrete input and output of a specific invocation. The transaction coordinates candidate computation and publication. `eligible` expresses preconditions on exact inputs and parameters. It may return a counterexample, an unsupported condition, or an accepted witness. `prepare` constructs content and edits. Obligations are selected by policy and discharged against the frozen candidate. Publication advances an accepted head after successful checks. [Hoare, An Axiomatic Basis for Computer Programming](https://doi.org/10.1145/363235.363259), [Pnueli, Siegel and Singerman, Translation Validation](https://link.springer.com/chapter/10.1007/BFb0054170).

~~~ts
Transformation<Inputs, Outputs, Params, Effects> {
  needs: AnalysisQuery<Inputs>[]
  eligible(inputs, params, facts): Eligible<Witness> | Ineligible | Unknown
  prepare(inputs, params, facts, witness, draft): Candidate<Outputs>
  obligations(inputs, candidate): Obligation[]
}
evaluate(transform, inputs, params, policy, execution): Receipt
~~~

The receipt includes invocation and policy versions, exact inputs and outputs, status, consulted facts, observations, edits, and lineage. Identity is an explicit outcome with its own receipt and any required input obligations. Policy decides whether the identical candidate can reuse a check. The capability type models ambient effects such as local compute, resource writes, and remote execution. Ineligible shapes, invalid candidates, failed checks, and failed infrastructure receive different outcomes. A strategy may recover from the first or from a policy rejection that it has explicitly opted into handling. A runner or adapter fault should remain visible as a failure.

Two instances are Typed LICM (same-kind, loop facts and a write set) and Tix-to-CUDA (cross-kind, multi-port, remote executor). A T6 tile transform supplies preconditions on a chosen loop and parameters. The extension absorbs domain wrappers and separates transform eligibility from profitability and postvalidation. Retain the core task runtime for flowing dependencies and the strategy interpreter for composing choices. P1 and P2 show the two runtimes need an explicit acceptance boundary and that sync kernels fit the existing async strategy semantics. `src/typed/passes.ts:423`, `src/tensor/cuda-contract.ts:203`, `T6-D/src/tensor/schedule.ts:539`, `src/framework/core/runtime.ts:447`, `src/framework/passes/bridge.ts:29`.

**Conjecture.** Make the artifact graph a DAG of attempts with multiple input and output ports, and make its accepted heads sparse references into it. A simple named pipeline is a path through that graph. For a shared store, candidate content may be addressed before commit, while readers of accepted heads see either the old tuple or the entire accepted tuple. Run effects through a journal or staged resource port. Where external effects cannot be rolled back, treat them as isolated measurements or explicit post-commit operations. A synchronous host and an asynchronous host can interpret the same state transitions. Defer a shared generator/effect interpreter for whole strategy programs until its value exceeds the public API change or the cost of running a pure plan asynchronously. MLIR's Transform Dialect provides a precedent for control IR and recoverable failure classes. [MLIR Transform Dialect](https://mlir.llvm.org/docs/Dialects/Transform/).

### 2. Translation-validation obligations and independently keyed observations

**Evidenced.** Describe a guarantee by the semantic relation, quantified input domain, side conditions and observation model. An evidence method describes how a result was established. A policy specifies the evidence it accepts. These are distinct from the outcome. Exact equality over four cases is a sample. Exhaustion over a finite domain covers exactly that declared domain. A proof kernel verifies a particular formal claim and has a stated trust base. Preserve counterexamples, skips, and undecided inputs as data. Use a closed discriminated union and default to `unknown` if no recognized evidence accompanies a status.

~~~ts
Obligation { semantics, relation, quantifiedDomain, observations, scope, assumptions }
Evidence { obligationDigest, producer, dependencies, outcome, method, coverage, witness }
ObservationJob<C, O> { cases, engines, runBatch(cases): Observed<O>[] }
ValidationPolicy { requirements, acceptableMethods, fallback, budgets }
~~~

Keep separate identities for generated cases, each side's observations, and paired verdicts. A mathematical precondition of reuse is that all relevant outputs are a function of the key. Default to exact pinned artifact, semantic options, executor and resource fingerprints. A reachable-function slice or normalized schedule key must declare a validated dependency read set or be checked against an uncached execution in audit mode. F26's case digest validates a part of that dependency relation. Probe P1 demonstrates the gap under a broken key. This is analogous to early cutoff and verified dependencies in incremental build systems. `src/framework/contracts/differential.ts:55`, `src/framework/contracts/differential.ts:200`, `src/framework/contracts/differential.ts:244`, `src/framework/core/runtime.ts:731`. [Mokhov, Mitchell and Peyton Jones, Build systems à la carte](https://www.microsoft.com/en-us/research/publication/build-systems-a-la-carte/).

Two instances are the Typed meaning-worker executor and the Tix remote CUDA batch. For GPU-only evidence, make batch execution an explicit alternative to providing synchronous per-case callbacks. For Typed local rewrites, use verified rule receipts as one evidence producer. For T6, an independent order validator discharges a constrained scheduling obligation and a separately configured CUDA run supplies end-to-end evidence. Options such as NaN-class or signed-zero policy, trap equivalence, target profiles, and error bounds belong in the claim. `src/typed/meaning-exec.ts:14`, `src/tensor/cuda-contract.ts:105`, `src/tensor/cuda-contract.ts:131`, `src/typed/rules/verify.ts:63`, `T6-J/src/tensor/schedule.ts:309`.

**Conjecture.** Compose exact refinements across a common semantics when intermediate claims and assumptions align. In a metric preserving comparison space, adjacent bounded errors can sum by the triangle inequality, subject to explicit transport of their domains and units. An implementation that rechecks relative tolerance against its immediate predecessor can drift under repeated composition. Prefer the existing fixed-origin check where a composed bound is unavailable. Prove equal reduction event sequences for the strict floating-point subset before attempting algebraic equivalence under a declared numerical model. Independently validate emitted code's precision, evaluation order and guards. Schedule-order witnesses alone cover the schedule semantics. `src/tensor/index.ts:42`, `src/tensor/contract.ts:100`, `src/tensor/cuda-source.ts:241`.

### 3. Witnessed edits and guarded local rewriting

**Evidenced.** Extend the generic edit protocol with a scoped rule-application witness and an explicit entry/root relation. Directed term or graph rewriting matches a pattern, checks side conditions and instantiates a replacement in context. Group the atomic edits that implement one rule occurrence. Store rule/version/fingerprint, substitutions, region and effects, before/after fragment digests, and the verifier's referenced evidence. The checker replays the local schema and verifies contextual side conditions such as domination, type, strict arithmetic, use counts, evaluation order, and external uses. A declared edit category is useful for auditing and carries no assurance on its own. `src/framework/ir/rewrites.ts:30`, `src/framework/ir/transactions.ts:88`, `src/typed/rules/compile.ts:93`, `src/typed/rules/verify.ts:87`. [Visser, Stratego](https://eelcovisser.org/publications/2001/Visser01.pdf).

~~~ts
applyRule<Fragment>(rule, target, substitution, localFacts): EditGroup
EditGroup { editIds, touchedScope, ruleApplication?, lineage }
edit.setRoot(region, role, target)
validateApplication(group, before, after, verifiedRule): Evidence
~~~

Typed fold/simplify and the A0 classification census are immediate uses of producer-supplied witnesses. Tix single-use inline is a second language instance of guarded rewriting with affine substitution and source occurrence lineage. B1 residual entry and D1 LICM preheader formation are immediate consumers of root-aware structural edits. Preserve generic matching alongside the native builders. Use explicit entry checks and region dominance validation. Tix expression projection and strict arithmetic rule evidence are testable extensions. A provenance witness from a legacy classifier should remain retrospective evidence with an explicit origin. `src/typed/rules/passes.ts:14`, `A0-G/src/typed/edit-classes.ts:283`, `src/tensor/passes.ts:21`, `B1-G/src/typed/specialize-buffer.ts:294`, `src/typed/passes.ts:423`.

### 4. Scoped lineage and additive execution attribution

**Evidenced.** Generalize correspondence as revision-scoped lineage with each port naming its entity universe. A visible graph, a lowering map, and a runtime observation can use different scopes. A trace map exposes a relation to its immediate antecedents. Keep use-site, inserted, removed, split, and merged entities explicit where available. Preserve edge history so a forward composition and a route back through pass decisions are both available. Use the proven geometry of relational composition already implemented by `composeCorrespondence`. A well-typed edge can still describe the wrong derivation (P4). ### 6. Dependence relations and validated schedules

**Evidenced for Tix; Typed lifting is conjectural.** Separate a description of computation from its schedule. An affine region supplies domains and access relations indexed by iteration points. ## Root changes and alternatives

~~~mermaid
flowchart LR
    I[Input revisions and parameters] --> F[Query analysis facts]
    F --> E[Check eligibility]
    E --> C[Prepare candidate and draft]
    C --> V[Discharge policy obligations]
    V --> P[Publish accepted heads]
    E --> R[Record attempt and evidence]
    C --> R
    V --> R
    P --> R
~~~

A transformation and its receipt give the layers a common semantic boundary. IR projections define what can be inspected and edited. Graph and dependence providers compute facts. Policy defines admissible evidence. Strategy decides which transition to request next. Aim for a single interpretation of identity, rollback, and publication. Prefer the native fast path for building candidates whose edits can be independently checked. The split between core tasks and pass declarations, and the separate preparation paths for native and editable results, are the first boundaries to test. `src/framework/core/types.ts:80`, `src/framework/passes/define-pass.ts:193`, `src/framework/passes/define-pass.ts:302`.

| --- | --- |
